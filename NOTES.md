# Заметки к решению

## Задача 1. Распределение заказов

**Что сделано**
- Баг: в `findNearest` у филиала были перепутаны `lat` и `lon` при вызове `distanceKm`.
- Правила `pickup_point`, `city` и «geo среди филиалов города заказа».
- Дневной лимит: `assignBranch` получает функцию `assignedCount(branchId)` и сама хранилище не читает, поэтому её легко тестировать. Сутки считаются по Алматы (`almatyDate`).
- API: `POST /orders/:id/assign` (повторный вызов возвращает сохранённое распределение и не занимает лимит), `GET /branches/:id/load`. Логика вынесена в `dispatcher.ts`, сервер только разбирает HTTP.
- Тесты: все `test.todo` закрыты, добавлены тесты на лимит, идемпотентность, границу суток и проверку даты.

**Допущения**
- Сохраняется любой результат, включая `unassigned`: повторный вызов возвращает его же. Если позже появится место, заказ сам не перераспределится — для этого нужен отдельный сценарий.
- Если выбранный филиал заполнен, запасной ищется среди всех активных филиалов магазина, как написано в README. Если у заказа нет координат, запасной найти нельзя — `unassigned`.
- В `GET /branches/:id/load` сначала проверяется дата (`400`), потом филиал (`404`).
- Часовой пояс Алматы считается фиксированным UTC+5.

**Несколько экземпляров с общей БД**
Сейчас гонок нет: один процесс, `assign` синхронный. С несколькими экземплярами два запроса могут одновременно занять последнее место в филиале или дважды распределить один заказ. Что бы изменила:
- Распределения хранить в таблице с `PRIMARY KEY (order_id)` и вставлять через `INSERT ... ON CONFLICT (order_id) DO NOTHING`: если строка уже есть, вернуть существующую. Это идемпотентность на уровне БД.
- Загрузку хранить счётчиком `(branch_id, date, assigned)` и занимать место атомарно: `UPDATE ... SET assigned = assigned + 1 WHERE branch_id = $1 AND date = $2 AND assigned < $limit`. Если обновилось 0 строк, филиал заполнен — пробуем следующий. Вставка распределения и счётчик — в одной транзакции.
- Никакого состояния в памяти процесса (`Map`) — всё в БД.

## Задача 2. Онлайн-запись

**Что сделано**
- Баг: интервалы полуоткрытые `[start, end)`, поэтому в `overlaps` сравнение строгое — запись 11:00–12:00 не пересекается с 10:00–11:00.
- `getSlots`: перерывы, активные записи мастера, прошедшее время. Текущее время передаётся параметром (по умолчанию `now()` из `clock.ts`), поэтому тесты не зависят от `NOW`.
- API: слоты, создание записи, отмена. Логика — в `booking.ts`, методы возвращают `{ status, body }`.
- Телефон нормализуется в `+77012345678` (`phone.ts`).
- Двойное бронирование: проверка слота и вставка выполняются под блокировкой по мастеру (`lock.ts`). Тест запускает два бронирования одновременно; без блокировки он падает.

**Допущения**
- `start` обязательно с часовым поясом (`Z` или `±HH:MM`). Время не на сетке слотов (например, `15:05` или с секундами) — `409`.
- Нет мастера или услуги при создании — `404`, как в API слотов; мастер не оказывает услугу — `400`.
- Принимаются только мобильные коды операторов Казахстана (700–708, 747, 771, 775–778). Городские номера вроде `+7 727 ...` отклоняются.
- Отменить ровно за 2 часа до начала ещё можно (`409` только если осталось меньше 2 часов).
- Отмена выполняется без блокировки: в худшем случае параллельное бронирование не увидит только что освободившийся слот, это безопасно.

**Одновременные бронирования при нескольких экземплярах и PostgreSQL**
Блокировка в памяти работает только внутри одного процесса. С несколькими экземплярами защиту нужно перенести в БД:
- Основной вариант — exclusion constraint (нужно расширение `btree_gist`):
  `EXCLUDE USING gist (master_id WITH =, tstzrange(start_at, end_at, '[)') WITH &&) WHERE (status = 'active')`.
  Вторая пересекающаяся запись не вставится, Postgres вернёт ошибку `23P01`, её превращаем в `409 slot_unavailable`. Правило гарантирует сама БД, даже если в коде ошибка.
- Альтернатива: в транзакции перед проверкой слотов взять блокировку мастера — `SELECT ... FROM masters WHERE id = $1 FOR UPDATE` или `pg_advisory_xact_lock`. Тогда бронирования одного мастера выполняются по очереди во всех экземплярах.
- Я бы выбрала exclusion constraint и оставила проверку слотов в коде, чтобы отдавать понятную ошибку.
